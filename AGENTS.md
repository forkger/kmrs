# AGENTS.md

Rules for working in this repository. They apply to humans and agents alike.

## Layout

- Rust workspace: `crates/komga-core` (shared primitives), `crates/komga-db` (SQLite, DAOs, migrations), `crates/komga-media` (analyzers, metadata readers), `crates/komga-search` (tantivy), `crates/komga-server` (HTTP API, config, services). `xtask/` holds dev tasks.
- HEIF, HEIC and AVIF decoding links static libheif, libde265 and dav1d through the `prebuilt` feature of [kmworks/libheif-sys](https://github.com/kmworks/libheif-sys), a fork patched in with `[patch.crates-io]`. Its build script downloads them, so a first build needs network access or `LIBHEIF_STATIC_DIR`.
- `licenses/`: license texts for those libraries, shipped with every release; update them with the libraries.
- `webui/`: the kmweb React web UI (Vite + pnpm), embedded into the binary at build time (rust-embed over `webui/dist`, placeholder page when absent) and served at `/`, version-locked to the server. Its own `webui/AGENTS.md` applies inside.
- User documentation lives in the kmworks/website repo (`docs/server/`), served at kmworks.date/server.
- `examples/config.toml`: the canonical all-keys configuration reference.
- `crates/komga-db/schema-main.sql`: reference schema of the main database (generated by `cargo xtask dump-schema`, do not edit by hand).
- `tests/diff/`: differential test harness that compares kmrs against a live Java komga instance.

## Compatibility (the core promise)

kmrs is a drop-in, data-level compatible reimplementation of [gotson/komga](https://github.com/gotson/komga); the compatibility target is **komga 1.30.1**.

- The schemas of `database.sqlite` and `tasks.sqlite` are byte-for-byte the Java Flyway migrations. `crates/komga-db/tests/schema_contract.rs` enforces this by running the vendored migration files (`crates/komga-db/migrations*`) against the Rust migrator.
- kmrs-private state never goes into the main database. It lives in `kmrs.sqlite` — its own migration track (`crates/komga-db/migrations_kmrs/`, `kmrs_migrations()`), its own connection, its own config key (`kmrs-db` / `KOMGA_KMRSDB_FILE`) — so the Java version can always open a kmrs-written data directory. The one exception is a kmrs-only server setting: it may be a `SERVER_SETTINGS` row keyed with a `KMRS_` prefix, because the Java version only reads the keys it knows and ignores extra rows. It is exposed as an optional field on `/api/v1/settings`.
- Any release must upgrade straight to the newest one: the desktop updater installs the latest release (`releases/latest` in `service/desktop_update.rs`), so a user several versions behind skips everything in between. The main databases follow Komga's cumulative Flyway migrations; the `migrations_kmrs/` track must stay cumulative the same way. Never edit or remove a released migration, and never write one that relies on code from an intermediate release having run.
- When porting behavior, verify against the Java/Kotlin sources, never from memory.
- Actuator endpoints and metrics that only expose JVM/Spring internals (beans, env, loggers, mappings, `system.*`, `jvm.*` beyond `jvm.memory.used`, ...) are intentional scope exclusions, not gaps.
- `/actuator/**` is a pure compatibility surface, frozen at Java parity: never add endpoints or response fields there (kmrs-specific additions go under `/api/**`), and leave existing behavior alone unless fixing a parity bug. The one intentional exception is `/actuator/shutdown`, dropped for security (the Java version allows it anonymously); kmrs has no HTTP shutdown endpoint at all.
- Server port, context path, and the kepubify path are configuration-only: the Java version also honors database overrides from the settings UI, kmrs never reads them (`PATCH /api/v1/settings` silently ignores the three fields; `server.context-path` only prefixes generated links, routes are not mounted under it). `koboPort` is dropped entirely — Kobo download URLs are built from the request's Host as-is (a reverse proxy is the supported deployment).

## Versioning

- The version lives in the workspace root `Cargo.toml` (`workspace.package.version`); crates inherit it via `version.workspace = true`.
- Bump the version only when the user explicitly asks, and always as its own dedicated PR (`chore: bump version`) once the feature work it covers is merged — never folded into a feature PR. Bumps are patch-level by default, features included; a minor bump is only for an explicitly called-out milestone.

## Configuration keys

A new configuration key must land in all three places: the loader/render (`crates/komga-server/src/config/`), `examples/config.toml`, and `docs/server/configuration.md` in the kmworks/website repo.

## Documentation

User docs live in the kmworks/website repo (`docs/server/`); edit them there. The pages that describe this repo's behavior:

- `limitations.md`: accepted gaps that are not planned to be closed (e.g. Lucene fuzzy/slop queries).
- `enhancements.md`: improvements over the Java version, plus intentional behavior differences.
- `compatibility.md`: parity target and the differential harness; links to the two pages above.

## Comments

- Comments say why, never what. No migration history ("no longer", "previously", dates, codenames) — the code and git history already say that.
- Assertions about dependency behavior (stdlib, crates) must be checked against the dependency's source before writing them down.

## Tests

- Pin contracts, not internals. A test asserts what callers and users observe — output shape and validity, spec'd constants, error paths — never the implementation's own geometry, layout, or encoder details; those rot with every refactor and turn the suite into a mechanical-update ritual. For generated visual output (cover collages and the like) the contract is just the no-crash guarantee: any input renders a valid image of the expected size, plus spec'd constants (e.g. empty collage → neutral gray).
- A regression test is trusted only after it has been shown to fail against the pre-fix behavior.

## Checks and workflow

- CI: `cargo fmt --all -- --check`, `cargo machete`, `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`, `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --all-features --no-deps --locked`, `cargo nextest run --workspace`, builds on ubuntu/macos/windows, docker. Keep Clippy and rustdoc warning-free.
- PRs are in English (title, body, comments).
- Reference issues in PRs with `Related to #...` by default. Do not use automatic-closing keywords (`Closes`, `Fixes`, `Resolves`) unless the user explicitly requests closing the issue.
- Squash-merge with a hand-written commit message (`gh pr merge --squash --subject ... --body ...`), never the default message, and without `Co-Authored-By` trailers.
